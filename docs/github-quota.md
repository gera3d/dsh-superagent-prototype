# GitHub quota behaviour

**Existing efficiency (unchanged):** repository streams (`issues`, `comments`, `review-comments`) send `If-None-Match` with the stored ETag, so an unchanged list returns HTTP 304 and costs no quota; notifications honour `x-poll-interval` (minimum 60 s). PR head/base/check facts and publication data are never cached or reused stale; they may only be revalidated (next paragraph).

**Revalidation of PR and CI reads (allowed) versus stale reuse (not allowed):** `readPull` (`pulls/<n>`) and `pullChecks` (`commits/<sha>/check-runs`, `commits/<sha>/statuses`) send `If-None-Match` with the ETag of the last 200 for that path. HTTP 304 costs no primary quota, and only then is the body stored from that 200 parsed again and returned, so the facts are as current as an unconditional read. A body is never returned without a 304 from the current call. The in-memory map is bounded (512 paths, least recently used dropped), is cleared on restart and is dropped for a path on any error or unparsable body. A list that spans several pages is read normally with `--paginate --slurp` and not remembered, as only a single-page response has one ETag. `fresh: true` on either function sends no `If-None-Match`. Publication, review and merge guards (`delivery-capabilities`, `lifecycle-decisions`, `finding-release`) make their own unconditional reads and are unchanged. An idle open PR therefore costs no counted request per round after the first, about 180 requests an hour saved per open ticket PR.

**Notifications `If-Modified-Since`:** the first-page notifications read sends the `Last-Modified` value stored by the last round that finished reading the list (`github-notifications`, with the last `x-poll-interval`). HTTP 304 counts as zero notifications and costs no quota, and the rest of the round runs as before: the retry map is read, the `since` cursor advances and the 60 s minimum interval applies. The `x-poll-interval` printed with the 304 headers is used, otherwise the last known interval. The header is stored in the same atomic step as the cursor, so a round that stops early or fails never stores a new one. A 200 with `rel="next"` pages as before, without the condition on page 2 onwards; a 304 for a request that sent no condition is an ordinary failure. The first run has no cursor and sends none. Expected saving: about 60 requests an hour per profile while idle (not measured against the real account).

**Added:** a failed `gh api --include` now keeps only status, `x-ratelimit-remaining/reset` and `retry-after` (`CliError.rate`). A primary limit (403 with remaining 0) waits until the reset; a secondary limit (429, or 403 with `retry-after`) waits `retry-after` (60 s if absent). Both add up to 10 s jitter and preserve the server deadline, splitting long waits into one-hour sleeps. Health shows `paused: GitHub <kind> rate limit reached; polling resumes after <time>`; the next successful round reports `ready` again with no restart. Permission/auth (401, 403 without quota signals), 304 and 5xx keep the ordinary `pollFailures` path. Local workers are unaffected: only the GitHub poll loop sleeps.

**Measured mocked workload:** the rejected first patch made four requests after an initial notification quota failure; the corrected production poll round makes one. A separate production-plugin fake-clock test records one request at the quota response, no further request during 7,199.999 seconds, and a second request with ready health at 7,200 seconds. No real account was exhausted or load-tested; account-wide usage is not attributed to Harness.

**Quota facts (official docs):** an authenticated user has 5,000 REST requests/hour shared across all that user's PATs, OAuth and user-authorized apps, so non-Harness consumers can drain it; Harness cannot attribute them. A GitHub App installation has a separate budget (minimum 5,000/hour, scaling with repos/users, higher on Enterprise Cloud). A paid personal plan does not raise the user limit. Moving to an App is a future option needing App registration, installation and a private key (new credentials and permissions), so it is not done here.

**Startup deployment check:** when the check ends in `githubRateLimited`, the runtime stays paused (`setupPending`) and schedules one `setup.restart()` instead of waiting for a person. It reads the primary reset with `gh api rate_limit --jq .resources.core.reset` through the same probe (this endpoint does not count against the quota) and restarts at the reset plus up to 10 s of jitter; the health detail names that time (`setupRetry`). If the reset cannot be read, or is already past because the limit persists (for example a secondary limit), it retries after 10 minutes, doubling per consecutive failure (20, 40, then 60 minutes at most). The consecutive-failure count is kept in the state database across restarts and cleared when setup succeeds or fails for another reason. Stopping the runtime clears the timer, and a manual check or settings save restarts earlier. Both setup requests that reach GitHub (`api user`, repository access) classify quota text, including "rate limit already exceeded" and HTTP 429, as `githubRateLimited` rather than `agentCliSignedOut`.
