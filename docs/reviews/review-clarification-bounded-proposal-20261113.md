# Proposed bounded repair: protected review clarification

Status: proposal only. No implementation, dispatch, settings change or approval inferred.

The existing output-efficiency release is stalled because native review receives the original seven requirement strings and the source diff, but not later operator-approved scope clarification. PR105's reviewer consequently asks to bound `isError` text while the current coordinator instruction explicitly requires that text to stay whole. Repeating the same review or changing the visible Senior Developer character cannot resolve that input mismatch.

## Recommended change

Add one operator-confirmed, append-only review clarification to an existing delivery. Preserve its original requirements, jobs, failed reviews, intake and authority. Supply the validated clarification alongside those original requirements on the next independent review. This creates a different, properly contextualized review attempt; it does not turn a failed verdict into a pass.

Do not implement a general scope editor, waiver, new queue, new reviewer framework, automatic approval or model/account change. Do not change original requirements or use external observations as authority. A fresh parallel delivery with replacement requirements is not an acceptable shortcut around the original finding lineage.

## Exact pilot clarification to present for approval

Original requirement (kept verbatim):

> Bound actual oversized tool stdout in the owned consumption path while retaining full durable logs, retrieval pointers, error/exit information and explicit truncation.

Proposed approved interpretation for this release:

> Bound successful shell and search tool text. A result marked `isError` must remain fully visible and unchanged, including its error flag and diagnostics. Oversized error output is intentionally excluded from bounding and savings claims; report that limitation explicitly. Preserve the full saved text, retrieval pointer and terminal status for every bounded successful result, or leave the original result unchanged when those guarantees cannot be met.

The other six intake requirements remain applicable without amendment. The clarification grants no merge, deployment, access, spending or acceptance authority. An independent reviewer must still report any real defect, including compact-tail loss or incomplete evidence.

## Minimal behavior and authority

- Only the same protected native operator boundary that already guards intake/release may confirm the exact addendum. Its preview must show original requirement, clarification, finding/job/delivery revision and exact head/base/patch. Observer, model, worker and generic inbox data cannot create this authority.
- Store an immutable record containing operator provenance, approved text, original requirement hash, finding/job/delivery identity, exact artifact pins, time, context digest and supersession history. Do not trust an actor name or approval claim embedded in source, reports or occurrences.
- Addenda can be confirmed only while the delivery is parked and no review/publication lease is productive. Stale revisions, changed jobs/heads/patches, foreign evidence and replay conflicts fail closed.
- Next review consumes original requirements plus server-validated addenda. Only the validated scope record defines the clarification; code, worker reports and arbitrary text remain untrusted data.
- Include context digest in review fingerprint/cache identity and retain the previous failed verdict. Start a fresh review within existing attempt/time/token/input limits; do not reset budgets or silently truncate mandatory context.
- Revalidation at publication must bind the passed review and clarification to the same exact artifact/context. Existing native Publish confirmation, rollback, live verification, evidence selection and requirement acknowledgment stay separate.

## Acceptance checks

1. Unauthorized observation/worker/source text cannot become a clarification; stale or foreign confirmations cannot act.
2. Original requirements, failed PR92/103/104/105 reviews, original finding/job and review budgets survive unchanged. No active review is canceled to add context.
3. A new review sees the approved error exception and does not reject error passthrough merely because it deliberately leaves errors whole. A separate seeded real defect must still fail review; approval of context never implies approval of code.
4. Review reuse, package preparation and publication reject a mismatched context digest or artifact pins. Existing protected publication/evidence gates remain intact.
5. Verify the actual original task thread: display the applicable clarification and the current next owner/action without asking the user to repeat completed work. No ordinary suggestion/reply is sent as a substitute for a protected action.

Use controlled fixtures for denied/replay/seeded-defect cases, not fabricated live failures. Run targeted checks, types and build on exact heads. Retain read-only/native versus controlled coverage labels.

## Work after that capability is qualified

Keep full errors, read/orchestration/non-text exclusions and all authority/reporting rules. The 4,025-byte pointer counterexample is exported-helper evidence, not a demonstrated native Mac hook failure.

Then use the protected clarification preview for the exact corrected candidate, independent contextual review, package/rollback, native Publish, deployment, actual-thread verification and separate evidence/acceptance. No deployment or successful release is promised by this proposal.
